## What's new in the app

- `/book` is now a real public booking page: visitors pick an open time slot and submit their name, email, and (optional) phone to book a free consultation call — no page reload, an inline "You're booked!" confirmation appears in place.
- Booking creates (or updates) a Contact, links or creates a Deal at the "Call Booked" pipeline stage, and pushes the event to Google Calendar and sends a confirmation email — both gracefully skipped with a console log until you add real credentials.
- The existing "Bookings" nav item (previously a "Coming soon" stub) is now the admin screen: set your recurring weekly availability, block off specific dates (vacation, one-off unavailability), and see/cancel upcoming calls.
- A new `/api/reminders` endpoint, meant to be hit by an external cron job once it's set up, sends a reminder email to anyone with a call in the next 24 hours who hasn't already gotten one.

## What was built

- **Schema:** `AvailabilityWindow` (`dayOfWeek`, `startTime`, `endTime` — recurring weekly rules), `BlockedDate` (`startDate`, `endDate`, `reason` — one-off exclusions), and `Booking` (`contactId`/`dealId`, `startAt`/`endAt`, `cancelledAt`, `googleCalendarEventId`, `confirmationSentAt`, `reminderSentAt`). `Booking.contact` uses `onDelete: Restrict` (same reasoning as `Deal.contact`); `Booking.deal` uses `onDelete: SetNull` with a nullable `dealId` (same reasoning as `Task.deal`) since the linked Deal may pre-exist or be newly created, and the Booking stays a valid historical record even if that Deal is later deleted. Status is a nullable `cancelledAt` timestamp, matching `Task.completedAt`'s existing convention rather than introducing this schema's first enum. Migration `prisma/migrations/20260914002204_add_booking_module`.
- **`src/proxy.ts`** — added `/api/reminders` to the public allowlist alongside `/`, `/login`, `/book`. This route does its own shared-secret check and isn't a browser-session route, so it must bypass the login-cookie gate.
- **Google Calendar** (`src/lib/googleCalendar.ts`) — one-way event push via `googleapis`, reading `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REFRESH_TOKEN` from `.env`. No in-app OAuth/consent UI, matching every other external integration in this app. No-ops with a console log if any var is unset.
- **Email** (`src/lib/email.ts`) — confirmation/reminder sending via `resend`, reading `RESEND_API_KEY`/`EMAIL_FROM`. Same graceful no-op pattern as `src/lib/storage.ts`.
- **Slot generation & conflict safety** (`src/lib/booking.ts`) — `getAvailableSlots()` expands `AvailabilityWindow` rules into 30-minute slots over the next 14 days, drops slots on blocked dates, drops past slots, and drops slots overlapping existing non-cancelled bookings. `hasOverlappingBooking()` re-runs the same overlap check inside a `prisma.$transaction` immediately before creating a Booking — an application-level safeguard against two visitors booking the same slot, verified directly (see below), not just assumed correct.
- **Admin screen** (`src/app/(dashboard)/bookings/`) — `actions.ts` (`setAvailabilityWindows` replace-all, `createBlockedDate`/`deleteBlockedDate`, `cancelBooking`), a weekly-grid `AvailabilityForm`, a `BlockedDateForm` + `DeleteBlockedDateButton`, and a `CancelBookingButton` for the upcoming-calls list. Reuses the sidebar's pre-existing "Bookings" nav item and its `page.tsx` stub instead of adding a new nav item — see Deviations below.
- **Public booking flow** — `src/app/book/page.tsx` + `src/app/book/actions.ts` (`createBooking`) + `src/components/BookingForm.tsx`. `createBooking` upserts the Contact by case-insensitive email (mirrors `submitLeadMagnet` from Milestone 5: never overwrites an existing `source`; new contacts get `source = "Booking"`), links to an existing Deal or creates one at "Call Booked" if the contact has none, then creates the Booking inside a transaction with the overlap re-check, then best-effort (non-blocking, try/caught) pushes the calendar event and sends the confirmation email.
- **Reminder endpoint** (`src/app/api/reminders/route.ts`) — the first Route Handler in this app. `GET` checks `?secret=` against `CRON_SECRET`, finds non-cancelled bookings starting in the next 24 hours with `reminderSentAt: null`, sends a reminder, and stamps `reminderSentAt` for idempotency.
- **`.env.example`** — added `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/`GOOGLE_REFRESH_TOKEN`, `RESEND_API_KEY`/`EMAIL_FROM`, `CRON_SECRET`.

## Decisions made during implementation that weren't pre-specified in the PRD

- **Google Calendar and Resend: env-var-driven, no in-app setup UI, both confirmed with you before implementation** — no Google Cloud project or Resend account exists yet. Booking, the Deal/Contact creation, and the admin availability screen all work fully today regardless; the calendar push and email sends just log and skip until real credentials are added. Same pattern as Milestone 5's local file storage.
- **Two models instead of the PRD's single `AvailabilityBlock` with a discriminator** — `AvailabilityWindow` (recurring) and `BlockedDate` (one-off) were built as separate models instead, because the fields that matter differ in kind (time-of-day vs. calendar-date) and a shared model would leave several columns nullable depending on which kind a row was. Same end-user behavior (recurring weekly hours + one-off date blocking); this is a schema-shape choice, flagged here rather than done silently, not a scope change.
- **The admin screen lives at the existing `/bookings` route, not a new `/availability` route** — the sidebar already had a "Bookings" nav item with a "Coming soon" stub page from earlier scaffolding (like `/leads` was pre-added in Milestone 4 ahead of Milestone 5). Building the availability manager and the upcoming-calls list there uses that pre-provisioned nav item instead of adding a redundant new one.
- **A real bug caught during verification, not assumed away**: `/book`'s slot list depends on the current wall-clock time in addition to live `Booking` rows, and Next.js statically prerendered it in a production build (confirmed via `next build`'s route listing showing `○` for `/book`) exactly like `/` was in Milestone 5 — except `revalidatePath` alone wouldn't be enough to fix it here, since the correct slot list changes purely with the passage of time (a slot becomes unavailable once it's in the past, and the 14-day window itself slides forward) with no write event to trigger a revalidation. Fixed with `export const dynamic = "force-dynamic"` on `src/app/book/page.tsx`; confirmed the rebuilt route listing shows `ƒ` (dynamic) instead. `revalidatePath("/book")` calls were also added to every availability-mutating and booking-creating action for the write-triggered half of freshness.
- **Double-booking safeguard verified under an actual race, not just assumed**: a Playwright script opened two separate browser contexts, both selected the identical open slot, and submitted within the same `Promise.all` tick. Exactly one booking succeeded; the other received the "That time was just booked by someone else" error from the transaction's overlap re-check — confirming the applicaton-level `$transaction` safeguard actually works under concurrency, not just in isolation.
- **Reminder idempotency verified directly**: with a seeded booking inside the next-24-hours window, the first `GET /api/reminders?secret=...` call returned `{"sent":1}` and stamped `reminderSentAt`; an immediate second call returned `{"sent":0}` — confirmed the endpoint is safe against being hit more than once by a cron misfire or retry.
- **A brand-new Deal created from a booking gets `valueCents: 0`** — there's no price being quoted at the "someone booked a call" stage, so 0 is the honest starting value; the coach can update it once a real offer is discussed.
- **Contact upsert on booking never overwrites `source` or `phone` if already set** — mirrors the case-insensitive-email upsert pattern from Milestone 5's `submitLeadMagnet` exactly, so a contact who already downloaded a lead magnet and then books a call keeps their original `source`, and a phone number is only filled in if the contact didn't already have one.

## Anything the next milestone will need to know

- **Google Calendar and Resend both still need real credentials before deploy** — obtaining a Google Cloud project + OAuth client + a one-time consent grant to get `GOOGLE_REFRESH_TOKEN`, and a real Resend account + `RESEND_API_KEY`, are both post-deploy steps this sandbox can't perform. Until then, calendar pushes and emails silently no-op with a console log — booking itself is unaffected.
- **External cron configuration for `/api/reminders` also can't be set up or verified from this sandbox** — someone (a real cron service, a platform's scheduled-functions feature, etc.) needs to be configured post-deploy to hit `GET /api/reminders?secret=<CRON_SECRET>` on a schedule (e.g. hourly) for reminder emails to actually go out.
- **Any future public/semi-public page reading from the database must consider whether it needs `force-dynamic`, not just `revalidatePath`** — this is a stronger version of the Milestone 5 lesson: `revalidatePath` only handles staleness from writes; a page whose correctness also depends on the passage of time (like `/book`'s slot list) needs `export const dynamic = "force-dynamic"` regardless.
- **`hasOverlappingBooking()` and the `SLOT_MINUTES`/`BOOKING_WINDOW_DAYS` constants live in `src/lib/booking.ts`** — reuse these rather than re-deriving slot or conflict logic if a future milestone touches booking (e.g. rescheduling).

## Deviations from the PRD and why

- Google Calendar and Resend are env-var-driven with no in-app setup UI, and the admin availability screen reuses the existing `/bookings` route instead of the PRD's implied separate screen — all explicitly agreed with you before implementation.
- Two availability models (`AvailabilityWindow` + `BlockedDate`) instead of the PRD's single `AvailabilityBlock` with a discriminator — a schema-shape deviation with identical end-user behavior, documented above.
- Rescheduling is out of scope per the PRD ("not in this milestone: two-way sync, rescheduling beyond cancel"); a plain cancel (`cancelledAt` timestamp + admin "Cancel" button) is implemented, matching that line's implication that cancel-only is in scope.
